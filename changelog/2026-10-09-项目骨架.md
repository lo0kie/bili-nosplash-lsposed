### 项目骨架

- 新建 `bili-nosplash-lsposed`：LSPosed 模块，目标是跳过 B 站启动时的白屏 / 启动屏。
- 构建体系：AGP 8.13.1 + Kotlin 2.2.20 + `compileSdk 36`，debug / release 两个构建类型，release 开混淆与资源收缩。
- 签名：从根目录 `keystore.properties` 读正式签名，**debug 与 release 共用**同一把，缺文件时退回 Android Debug。
- 模块元数据：`META-INF/xposed/{java_init.list,scope.list,module.prop}`，`minApiVersion` / `targetApiVersion` 都是 101。
- `BiliModule`：模块入口，`onModuleLoaded` 记进程名，`onPackageReady` 判包名 / 读版本 / 绑 `HostEnv` / 钩
  `Application.onCreate` 抓 Context。
- `HostEnv`：注入侧运行时环境（进程名 / 包名 / 版本 / ClassLoader / Context），宿主类型一律从它拿 ClassLoader 解析。
- `XLog` / `Reflect` / `hooks.kt`：日志出口、反射工具、`hookGuarded` 统一收口，语义与「输入法增强」那套一致。
- 界面：一开始是 Compose +
  Miuix 的最小状态页（启用状态、桌面图标开关、版本），跑在模块自己的进程里；同日认定模块不需要界面，已整个删掉（见下）。
- CI：GitHub Actions 构建 debug 与 release 两个 APK 上传 artifact，并按 `versionName` 发到 Releases。

### 启动屏深色化

- 作用域扩到第二个包
  `com.android.systemui`：冷启动那段白屏不是 App 窗口画的，是系统画的启动窗口（`Splash Screen tv.danmaku.bili`，`ty=APPLICATION_STARTING`），而本机（ColorOS
  / Android 17）画它的 WMShell 跑在 SystemUI 进程里。
- 白屏来源钉死为一份 drawable：启动页主题的 `android:windowBackground` =
  `tv.danmaku.bili:drawable/layerlist_splash`（白底 + 粉色字标，**没有 `-night` 变体**）。
- `SplashTheme`（App 侧）：钩 `Activity.onCreate`，在宿主自己的 `onCreate`
  之前把窗口背景换成「同一份 layer-list、第一层颜色换掉」的深色版；判据是「主题的 `windowBackground` 指到
  `layerlist_splash` 且当前是深色」，不按类名，换版本 / 换入口 Activity 都不会漏。
- `SystemSplashTheme`（系统侧）：钩 `Resources#getDrawableForDensity(int, int, Theme)` 收口 —— `getDrawable(int)` /
  `getDrawable(int, Theme)` 与系统那三个入口（`overlayDrawable` / `createIconDrawable` /
  `OplusShellStartingWindowManager.handleSplashScreenView`）全都走它，命中资源全名
  `tv.danmaku.bili:drawable/layerlist_splash` 时换成深色版，**谁最后写、写几次都只会写深色**。
- 判据用带包名的资源全名而不是资源 id：id 是 per-package 的，拿 SystemUI 自己的 id 比会误伤；按 `Resources`
  实例缓存「这个 id 是不是它」，非命中进否定缓存，稳态下只有一次哈希查找。
- 颜色不硬编码：拿 `<application android:theme>` 单独套一份 theme 问它 `windowBackground`，深色下解析出 `@color/Ga1`
  的 night 值 `#0a0b0c`；解析不到才退回常量。
- 深色版按「第一层颜色换掉、logo 层照搬」**重建**（每层 `constantState.newDrawable()`），不就地改 `Resources`
  缓存实例，避免用户在 App 内切回浅色时复用被改黑的 drawable。
- `SplashViewBuilder` 上的三个参数 Hook（`setWindowBGColor` / `overlayDrawable` /
  `createIconDrawable`）保留为兜底，覆盖「drawable 不经 Resources」的路径。
- 真机验证：3 次冷启动、约 90 帧采样，白屏帧数为 0；最早一帧起就是 `#0a0b0c` 铺满 + `#fb7299` 粉色字标。

### 第三层：App 自己的品牌启动页（收尾那段白屏）

前两层（系统启动窗口 +
Activity 窗口背景）都做完之后仍有白屏，时机是「深色启动屏之后、首页出来之前」。线索是用户提的：另一个模块（哔哩漫游）能去掉这一段，关掉就回来。反汇编
`me.iacn.biliroaming` 的 `biliroaming.Ah#afterHookedMethod` 确认它挂的是
`BaseBrandSplashFragment#onViewCreated(View, Bundle)`，夜间时对 `R.id.splash_container` 设黑色。

- **白底在哪**：品牌启动页的**根 view 就是** `splash_container`，`android:background="@color/white"`
  写死在布局里（两版同为 `res/W0I.xml`，结构一模一样），没有任何夜间变体 —— 所以这一段只能靠 Hook 改。
- **做法**：Hook `tv.danmaku.bili.ui.splash.brand.ui.BaseBrandSplashFragment#onViewCreated`， `chain.proceed()` 之后取
  `args[0]`，`findViewById(splash_container)` 命中就 `setBackgroundColor(深色)`。颜色仍走
  `nightWindowBackground`，与另外两层同源（`#ff0a0b0c`）。
- **判据是 id 不是类名**：`splash_container` 用名字解析（两版 id 不同：8.34.0 `0x7f093d58` / 9.13.0 `0x7f0941e9`），
  `findViewById` 不到就原样不动。类名解析不到时退到父类
  `com.bilibili.lib.ui.BaseFragment`，靠这条 id 判据保证不误伤别的页面。
- **为什么前几轮没测出来**：**这一层只在「从桌面图标启动」时才出现**。`am start` 冷启动时 `mCallingUid` 是
  `2000 (com.android.shell)`，B 站直接跳过品牌启动页；改成点桌面图标（`mCallingUid=10239 (com.android.launcher)`）才复现。
- **A/B 实测**（PLK110 / 8.34.0，桌面图标冷启动，60fps 抽帧逐帧算平均亮度 0–255）：

  |             | 帧序列（平均亮度）                                    | 白屏帧 |
  | ----------- | ----------------------------------------------------- | ------ |
  | 关掉本 Hook | `64 → 11 → 25 → 233（连续 41 帧 ≈ 0.68s）→ 42 → 首页` | 41 帧  |
  | 开着本 Hook | `64 → 11 → 30（品牌启动页深色底 + 字标）→ 42 → 首页`  | 0 帧   |

- 两台设备均复测通过：PLK110 / 8.34.0 最大亮度 92、0 白屏帧；PJD110 /
  9.13.0 品牌启动页 Hook 命中（`品牌启动页已跟随深色模式：androidx.constraintlayout.widget.ConstraintLayout → #ff0a0b0c`），其后屏幕上出现的是品牌启动图本身（浅色广告图），不是白底。
- 9.13.0 新增了一套 Compose 冷启动（`kntr/srcs/app/splash/startup/SplashContainerFragment` +
  `BrandSplashPageKt`），但实测走的仍是 `BaseBrandSplashFragment` 这条路，Compose 那套没被触发。

### 第四层：收尾那条白其实来自「没生效的系统启动窗口」

- 现象：品牌启动页深色化之后，冷启动过渡还剩**底部一条满宽白条 + 居中粉色 bilibili 字标**，约 40ms（设备 1 原片 720x1570
  / 106.85fps 第 431–435 帧，t≈3.59–3.63s）。
- 几何上它就是**一份满屏 `layerlist_splash` 的底部 79px**：白底 + 底部居中、距底 16dp 的
  `ic_logo_default`。设备密度 560dpi、录制 720:1272 折算后，预测字标范围（行 1444–1505
  / 列 290–427）与实测（行 1490–1504 / 列 298–425）吻合。
- **真正的原因**：SystemUI 那一半（`SystemSplashTheme`）在设备 1 上**从来没生效过**。判据是日志 ——冷启动（04:31、04:32 两次）里一条
  `系统启动窗口背景已换成深色版` 都没有，也没有 `模块已加载 | 进程=com.android.systemui`。`killall com.android.systemui`
  之后它立刻加载并打出：

  ```
  (com.android.systemui)[com.lookie.bilinosplash,...] 系统启动窗口背景已换成深色版：tv.danmaku.bili:drawable/layerlist_splash（id=0x7f081884）
  (com.android.systemui)[com.lookie.bilinosplash,...] 系统启动窗口叠层已换成深色版：LayerDrawable
  ```

  →
  **模块安装 / 更新后必须重启 SystemUI（或重启设备），系统启动窗口那一层才会生效**；否则那段启动窗口一直是白的，平时被 App 自己的窗口盖着，只在启动页退出动画的那几帧从底下露出来。这同时解释了「偶发」与「设备 2 看不到」（广告页盖住了）。

- 之前记的「广告启动页
  `logo_layout`」是**误判**：冷启动日志里广告页布局（`SplashContainerView`）根本没被 inflate，那条白不是它。
- 顺手加的 inflate 兜底（`View#onFinishInflate`）留着：它覆盖「品牌启动页被别的路径 inflate」的情形，成本是一次 int 比较；广告页那两支属于额外覆盖，与本次问题无关。
- 设备 1 上顺带把 logcat 缓冲调到 8M（`logcat -G 8M`）——默认缓冲太小，模块日志几秒就被冲掉。

### 第五层（白条的真正来源）：启动页资源下载页

前面几层全部生效（日志里 App 窗口背景、品牌启动页、资源收口、SystemUI 启动窗口都命中且是深色）之后**白条仍在**，于是改成纯静态逆向，两步就钉死了：

1. 把 APK 里 30 个 dex 全扫一遍 `layerlist_splash` 的资源 id（`0x7f081884`）的字节序列 —— 只有 `classes21.dex`
   里一处命中，且落在**数据段**（一张 id 数组），**没有任何代码引用它**。结论：这份 drawable 只会经主题的
   `windowBackground` 出现，不可能有别的代码路径凭空画它。
2. 再把 `res/*.xml` 全扫一遍粉色字标 `ic_logo_default`（`0x7f081310`）——只有三份引用： `res/gN5.xml`（=
   `drawable/layerlist_splash`）、`res/0Kt.xml`（广告启动页）、 `res/bub.xml`（**启动页资源下载页**）。

`res/bub.xml` = `layout/bili_layout_fragment_splash_mod_download`：

```
LinearLayout  android:background="@color/white"   ← 满屏白底，根上**没有 id**
  ├─ FrameLayout (weight=7) → ImageView(ic_splash_default) + TextView/进度条
  └─ ImageView  id=logo  src=@drawable/ic_logo_default  weight=1  scaleType=CENTER
```

满屏白 + 底部居中粉色字标，和实测那条白条（底部 79px、满宽、白底、字标底部露一截）几何完全吻合：按 560dpi /
720:1272 折算，该页底部 `logo` 区里字标的底边预测 ≈1498，实测 ≈1504。

- **做法**：`View#onFinishInflate` 那一层再加一支 —— 根 view 是**纯白底**、且同时含 `download_progress` + `logo`
  两个 id，就整页换深色（根上没有 id，只能靠子 id 组合认；单独一个都不够：广告启动页也有
  `logo`）。判据先做「根背景是不是纯白」的便宜检查，命中才 `findViewById`。
- 这解释了为什么前面几层怎么改都没用：它既不属主题、也不叫 `splash_container` /
  `SplashContainerView`，只在「启动页资源需要下载」时出现，所以偶发。

### 第六层：View 层收口 + 启动窗口背景缓存

白条仍在之后，转向反汇编**本机 SystemUI**（`reference/SystemUI.apk`，`classes3.dex`），拿到
`SplashscreenContentDrawer$SplashScreenWindowAttrs#getWindowBgImage(Context)` 的实现：

```
Resources res = ctx.getResources();
int uiMode = res.getConfiguration().uiMode;
if (mWindowBgImage != null && uiMode == this.uiMode) return mWindowBgImage;   // ← 缓存命中就返回
if (mWindowBgResId == 0) return mWindowBgImage;
mWindowBgImage = ctx.getDrawable(mWindowBgResId);   // Context.getDrawable → getDrawableForDensity
this.uiMode = uiMode;
return mWindowBgImage;
```

两个结论：

- 它取 drawable 走的是 `Context.getDrawable` → `Resources#getDrawableForDensity`，**理论上**被 `SystemSplashTheme`
  的收口盖住；
- 但它把结果**缓存在 `mWindowBgImage`** 里，只要 `uiMode`
  不变就直接复用 —— 缓存里若是白的，之后再怎么在取 drawable 那一层收口都没用。

于是加两层「最后一公里」的收口（App / SystemUI 各装一次）：

- **`View#setBackground(Drawable)`**：谓词是「第一层纯白 `ColorDrawable` + 第二层 360x180 的
  `BitmapDrawable`」= 启动屏那份 layer-list（`layerlist_splash` / `safe_mode_layerlist_splash`
  都是这个结构；第二层的尺寸判据是为了不误伤别的「白底 + 位图」layer-list）。命中就换深色版，并打一条日志 ——
  **日志本身就是探针**，能看出是哪个 view、什么时候被设成白底。
- **`SplashScreenWindowAttrs#getWindowBgImage`**：在它返回处再兜一次，让**缓存里存的也是深色**。

两台已装（`2026-10-09-0505`）并重启 SystemUI。

### 第七层（真凶）：App 侧夜色判据和 SystemUI 侧不一致

用户在 `0505` 上复现后，日志给出了决定性证据：**SystemUI 侧全部命中**（`系统启动窗口背景已换成深色版`），而
**App 侧一条都没有** —— 连新加的 `[app] 白底启动屏 layer-list 命中` 探针都没打。

对照两边的判据就清楚了：

|                               | 判据                                               |
| ----------------------------- | -------------------------------------------------- |
| `SystemSplashTheme`（系统侧） | `isNight(res) \|\| isNight(Resources.getSystem())` |
| `SplashTheme`（App 侧）       | 只有 `isNight(res)`                                |

冷启动那一瞬，**系统早已是深色、而 B 站自己的 `Resources` 还报浅色**（`AppCompatDelegate` 的夜间覆盖要等 Application /
Activity 走完才落到 configuration 上）。于是 App 侧五层（窗口背景、资源收口、View 层收口、品牌启动页、inflate 兜底）**全部提前 return**，窗口背景就留在主题里那份白的
`layerlist_splash`
上 —— 收尾那几帧露出来的就是它。这也解释了「偶发」：App 侧那次 configuration 是不是已经变成深色，取决于这次启动前 App 的状态。

- **修法**：把 App 侧的 `isNight` 对齐成和系统侧同一条（`App 深色 || 系统深色`），并在 `prepare()` 命中主题时打一行
  `启动屏主题命中：<类名> appNight=… systemNight=…` —— 之后再有白条，这一行能直接指出是判据问题还是别的问题。

### 白条的真正来源：ROM 在 system_server 里的启动画面

判据全部命中、探针一次没响之后，转去反编译设备上的 ROM 扩展：

- `/system/framework/oplus-services.jar` 里有 `com.android.server.wm.OplusStartingSurfaceController`、
  `OplusStartingSurfaceControllerBase`、`OplusStartingSurface`、`QuickStartUtils`、`OplusCaptureFile`、
  `StartingSurfacePreviewPolicy`，字符串含 `resolveStartingSurfaceLaunchType`、
  `preStartActivity cold start intent`、`preStartActivity not icon launch`、
  `getCapBitmapFileForStartingSurface`、`loadBitmapAndDrawSurface`、`supportSplashScreenPreview`。
- 它们由 **system_server** 执行（日志里那几行的 pid 就是 system_server），用 `SurfaceControl` 铺启动画面；模块作用域只有
  `tv.danmaku.bili` + `com.android.systemui`，**盖不到这个进程**。

实测把覆盖包启用/停用一遍之后，ROM 自己把 B 站的启动画面背景关掉了：

```
OplusPreStartController: isCapBitmapExists ... uiMode: 33, found captures: true
StartingSurfacePreviewPolicy: checkSupportSurfacePreview app not support, package: tv.danmaku.bili
OplusShellStartingWindowManager: ... splashScreenThemeResId 7f120064,
   exi: OplusStartingWindowExtendedInfo{ mIsExceptionListApp=true, mPreviewBitmap=null,
        mShouldDrawBackground=false, mQuickStartingSurface=null, ... }
```

`mIsExceptionListApp=true` + **`mShouldDrawBackground=false`**
—— 不再画那层背景，白条消失。这个标记大概率是 App 被覆盖包搞崩几次（`reason=4 APP CRASH`）换来的，**属于 ROM 侧状态、可能被重置**。

### 附：RRO 覆盖包（备胎）与它踩的坑

做了一个 RRO 覆盖包（`dist/bili-nosplash-overlay-*-magisk.zip`）：给 `tv.danmaku.bili` 提供
`drawable-night/layerlist_splash`（深色版），让**任何进程**（含 system_server）在深色下都解析到深色版。

- **坑（已踩）**：只提供 `night` 配置会让 App 直接崩 ——
  `Resources$NotFoundException: Drawable tv.danmaku.bili:drawable/layerlist_splash (#0x7f081884)`
  `at tv.danmaku.bili.MainActivityV2.e9 / onCreate`。原因是 `MainActivityV2.onCreate`
  自己就会取这份drawable，而那一刻它按**浅色**配置取（就是前面查到的「系统深色、App 资源还报浅色」），覆盖包里没有默认配置 → 取不到 → 崩。修法：覆盖包同时提供默认配置（内容与原版一致的白色版）和
  `night` 深色版。
- 因为 ROM 侧的 `mShouldDrawBackground=false` 已经生效，`service.sh`
  改成**不自动启用**，覆盖包只作备胎：白条若回来，手动 `cmd overlay enable --user 0 com.lookie.bilinosplash.overlay` +
  `am force-stop tv.danmaku.bili`。

> **后记**：覆盖包（RRO + Magisk 模块，曾放在 `overlay/` 与 `dist/`）与 `HANDOVER.md`
> 已按要求删除。结论保留：白条来自 ROM 在 system_server 里那套启动画面（带缓存/快照），改完启动屏**重启一次**才会重新生成；模块的日志里有一条同名说明（`ColorOS 启动画面：…`）。

### 结论修正：白条是「上一次开机的启动画面缓存」

用户在「卸载覆盖模块 + 重启」之后白条依旧没有回来，据此提出的猜测（**系统在一次开机的生命周期里缓存了启动画面**）与代码证据吻合，比上面「崩溃换标记」的说法更贴：

1. **进程内缓存**（反汇编 SystemUI `classes3.dex`）：

   ```java
   SplashScreenWindowAttrs.getWindowBgImage(Context ctx) {
       int uiMode = ctx.getResources().getConfiguration().uiMode;
       if (mWindowBgImage != null && uiMode == this.uiMode) return mWindowBgImage;  // ← 命中就复用
       mWindowBgImage = ctx.getDrawable(mWindowBgResId);
       this.uiMode = uiMode;
       return mWindowBgImage;
   }
   ```

   按 uiMode 缓存 drawable，**进程不重启就一直复用**。

2. **磁盘侧快照**：`QuickStartUtils.getCapBitmapFileForStartingSurface` / `OplusCaptureFile`，日志
   `isCapBitmapExists ... found captures: true`，配套 `TaskSnapshotCache.putSnapshot`
   （实测给 B 站抓过快照）。也就是还会把启动画面拍成位图留着用。

所以白条 =
**一份「旧的白启动画面」的缓存/快照**（拍的时候启动屏还没改深）；重启后缓存被用现在的（深色）画面重新填充，白条消失。`mIsExceptionListApp=true`
/ `mShouldDrawBackground=false` 大概率是 ROM 对这类 App 的既有策略，不是崩溃换来的（上一条推断作废）。

**实务结论（写进 README / HANDOVER）**：

- 装 / 更新模块后，**验证前先重启一次**，否则看到的是上一次开机的旧缓存；
- 这也解释了为什么单独重启 SystemUI 无效 —— 缓存不在 SystemUI 进程里；
- 白条若回来：先重启一次（让 ROM 的缓存/快照重新生成）。

### 补记：深色化是「两半」，只勾 SystemUI 也「看着生效」

用户两条实测互为对照：**只勾 `com.android.systemui` 不勾 `tv.danmaku.bili`** 时看着仍是深色；
**关掉哔哩漫游、两个包都勾**时也没白。原因就是模块注入两个进程、各管一层：

| 作用域里的包           | 管的是哪一层                                                                      | 漏了会看到什么                       |
| ---------------------- | --------------------------------------------------------------------------------- | ------------------------------------ |
| `com.android.systemui` | 系统启动窗口（WMShell 在 SystemUI 进程里画的那段）                                | 冷启动最开头那段白                   |
| `tv.danmaku.bili`      | B 站自己画的品牌启动页（`splash_container` 的 `@color/white`）+ Activity 窗口背景 | 系统启动窗口撤掉后、首页出来前那段白 |

只勾 SystemUI 时「看着没白」，是 B 站那一段没露出来（或只闪一两帧），不是它被改深了 ——这就是「不勾 bilibili 也生效」的由来。

**日志对照**（设备 1，`/data/adb/lspd/log/modules_*.log`）：两个包都勾的那几次冷启动里， `品牌启动页已跟随深色模式`
14 次、`系统启动窗口背景已换成深色版`
34 次；B 站被取消勾选那段时间，模块在 B 站进程里一条日志都没有（最后一次是 05:26）。

**与哔哩漫游的关系**：漫游的启动页 hook（类 `biliroaming.h6`，日志串 `startHook: Splash`，开关 `biliroaming_splash` /
`auto_dark_splash` / `purify_splash` / `custom_splash` / `custom_splash_logo` / `full_splash` /
`full_brand_splash`）改的**与本模块第三层是同一层** （`BaseBrandSplashFragment` +
`splash_container`），所以两者会互相掩盖：关掉漫游时如果 B 站那半没勾，就没人改这一层，白就回来。

**已知缺口（未修）**：`id/full_brand_splash`（`BiliImageView`）—— 品牌活动期间显示的那张 **全屏品牌图**，由 B 站从
`files/kstagger/brand_splash/<hash>/*` 读文件解码后塞进 ImageView，既不经过 `Resources`，也不是 `setBackground`
收口的判据（那张图是 ImageView 的 drawable，尺寸 1280x2560，不是 `layerlist_splash` 的「纯白底 +
360x180 位图」）。本模块只改了它的 **父容器背景**。缓存里实测有白底的图（1280x2560 均色 225.2
/ 白像素 62.8%），真显示时底改深也压不住。平时该 view 是 `GONE`，所以现在碰不到。
